# Решения по итогам explore (review-queue-task-filter)

Q1. Нечисловой и несуществующий параметр на /review -> 404 «Задача не найдена» (единый ответ).
    Изменение поведения (находка A): сейчас /review?task_id=abc -> 200 с полной очередью; станет 404.
Q2. Валидно только ASCII ^[1-9][0-9]*$ и <= 2^63-1. Всё остальное (0, -1, 05, " 5", +5, 5.0, 1_000,
    ٥, ², > 2^63-1, "   ") -> невалидно. Пустое значение -> без фильтра. Повтор параметра -> последнее значение.
Q3. По умолчанию: /login-редирект -> 403 для не-ментора -> только потом разбор. Параметр объявлен как str | None.
Q4. По умолчанию: разбор и проверка в app/services/reviews.py, роуты передают сырую строку,
    URL редиректа собирается только из id проверенной задачи.
Q5. Передача фильтра на страницу сдачи через ?<param>=N в ссылке «Открыть» (только при активном фильтре).
    На странице сдачи и в POST невалидный/несуществующий фильтр мягко игнорируется (ссылка и редирект на /review).
    Несовпадение с задачей сдачи допускается (фильтр сохраняется). Студенту параметр игнорируется.
    409/404 после POST рендерят error.html, фильтр там теряется - записать явно.
Q6. GET-форма action="/review", <select> по всем задачам, первый пункт «Все задачи» value="", кнопка «Показать».
    «Сбросить фильтр» при любом активном фильтре. Заголовок «Очередь ревью · <название задачи>».
    Форма показывается и при пустой очереди без фильтра.
Q7. Имя параметра и скрытого поля: assignment_id.
Q8. Текст ошибки: «Задача не найдена».
B.  500 на огромных id в baseline (/assignments/..., /submissions/..., POST ревью) - вне рамок этого change,
    записать в proposal как известную проблему; фильтр этот баг не повторяет.
