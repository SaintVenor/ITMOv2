# Research: построчные комментарии (логика)

Неясностей из Technical Context нет. Ниже решения и допущения плана (по Принципу V конституции).

## Решения

### R1. Хранение — одна новая таблица `line_comments`
- **Decision**: класс `LineComment` в `app/models.py`, таблица создаётся уже существующим `create_all` в `init_db`.
- **Rationale**: FR-002 и бриф запрещают менять существующие таблицы; `create_all` добавляет только отсутствующие таблицы, поэтому уже созданная БД работает без миграций.
- **Alternatives**: колонка в `submissions`/`reviews` (ломает созданную БД, отвергнуто); JSON-поле в `reviews` (ревью одно на сдачу, а комментариев много, и ревью может не быть).

### R2. Определение строки — `code.split("\n")`
- **Decision**: число строк = `len(submission.code.split("\n"))`, допустимы номера `1..N`.
- **Rationale**: шаблон `_code.html` уже показывает код через `code.split("\n")`; сервис `clean_text` нормализует `\r\n` в `\n` при сохранении. Номер строки у ученика и ментора совпадает по построению (FR-003). Пустые строки считаются.
- **Alternatives**: `splitlines()` (делит и по `\r`, `\x0b`, ` ` — номера разошлись бы с показом).

### R3. Разбор номера строки — строка, а не `int` в сигнатуре роута
- **Decision**: форма принимает `line: str = Form("")`; сервис принимает `str`, проверяет `re.fullmatch(r"[1-9][0-9]*", s, re.ASCII)`, затем сравнивает с числом строк.
- **Rationale**: `int` в сигнатуре FastAPI превратил бы `05`, `+3`, ` 3` в 422/404 или принял бы их; FR-005 требует каноничный вид и ошибку у поля `line`. Явный `[0-9]` вместо `\d` (как в `reviews._CANONICAL_ID`) отсекает «٣». Перед `int()` длина строки ограничивается 19 символами: больше цифр, чем у 2^63-1, заведомо вне диапазона (и защита от лимита `int()` на 4 300 цифр, из-за которого был бы 500).
- **Alternatives**: `int()` с `try/except` (`int()` принимает `05`, `+3`, ` 3` и `٣` — нарушает FR-005).

### R4. Порядок проверок: роль → сдача → ввод
- **Decision**: в роуте `Depends(require_mentor)` (даёт 403 для ученика раньше разбора формы; аноним перенаправляется middleware); в сервисе `ensure_role` → поиск сдачи (`NotFound`) → валидация `line` и `text` вместе (одно `ValidationError` с обоими полями).
- **Rationale**: FR-012 (права раньше валидации), FR-011 (`NotFound` для несуществующей сдачи), по образцу `reviews.create_review`.
- **Alternatives**: валидация до поиска сдачи (нельзя проверить диапазон строк без сдачи).

### R5. Текст — `clean_text(..., 2_000, "Комментарий")`
- **Decision**: переиспользовать `app.services.validation.clean_text`; `COMMENT_MAX = 2_000` в новом сервисе.
- **Rationale**: FR-006, FR-013: нормализация `\r\n`, strip, сообщение «не длиннее N символов (сейчас M)» как у остальных полей. Содержимое не санитизируется.

### R6. Чтение — через `get_submission_for`
- **Decision**: `list_line_comments(db, user, submission_id)` вызывает существующий `submissions.get_submission_for`: ментор видит любую сдачу, ученик только свою, чужая и вне диапазона id — `NotFound`.
- **Rationale**: FR-009…FR-011, повторное использование без копирования правил. Статус сдачи и наличие ревью не проверяются (FR-016, FR-017).

### R7. Порядок списка
- **Decision**: `ORDER BY line ASC, created_at ASC, id ASC` (FR-008). Индекс `(submission_id, line, created_at, id)`.
- **Rationale**: детерминированный порядок при равных временах; один запрос на список.

### R8. Атомарность и конкурентность
- **Decision**: один `db.add` + один `commit`, при исключении `rollback`. Уникальных ограничений на (сдача, строка) нет.
- **Rationale**: FR-007, FR-014: несколько комментариев к строке допустимы, параллельные вставки не конфликтуют; валидация идёт до `add`, поэтому частичных записей нет. Ревью и статус сдачи не трогаются (FR-015).

### R9. Автор — отображаемое имя через связь
- **Decision**: в ответе автор = `author.display_name` (связь `LineComment.author` → `User`); список грузится с `joinedload(LineComment.author)`.
- **Rationale**: FR-008; не раскрывать `username` и `password_hash`.

## Допущения плана

- **A1. HTTP-контракт — на стороне логики, внешний вид — на стороне UI.** Логика даёт маршруты и данные (`contracts/line-comments.md`); шаблон страницы сдачи правит команда UI. Общий файл `specs/line-comments-contract.md` отсутствует, поэтому этот контракт — единственный источник; при появлении общего он главнее.
- **A2. Маршруты**: `POST /submissions/{submission_id}/comments` (форма `line`, `text`; успех — `303` на `/submissions/{submission_id}`) и `GET /submissions/{submission_id}/comments` (JSON-список). Выбраны по образцу существующего `POST /submissions/{id}/review`.
- **A3. Ошибка валидации в форме**: `400` и повторный показ страницы сдачи (`render_submission`) с контекстом `line_comment_errors` (`{"line": ..., "text": ...}`) и `line_comment_form` (введённые значения). Конкретный вывод ошибок — зона UI.
- **A4. Контекст страницы сдачи** (`GET /submissions/{id}`) расширяется ключами `line_comments` (список из FR-008) и `line_count`. Существующий шаблон их игнорирует, поэтому страница не ломается до правок UI.
- **A5. JSON для GET** принят как формат данных для проверки и интеграции; это не JS на странице (ограничение «без JS» не нарушается).
- **A6. Коды ответов** следуют существующим: 404/403/400 (`ERROR_STATUS` в `app/main.py`); `Conflict` (409) в этой фиче не используется.
- **A7. Время создания** — `utcnow()` из `app/models.py`, тот же формат, что у `Review.created_at`.
- **A8. Сдача в пути с нечисловым id** (`/submissions/abc/comments`) — 404 через существующий обработчик `RequestValidationError`.
