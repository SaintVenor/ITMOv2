## User Scenarios & Testing *(mandatory)*

### User Story 1 - Ментор комментирует строку кода сдачи (Priority: P1)

Ментор открывает страницу сдачи и видит код с номерами строк. Рядом с каждой строкой есть действие «Комментировать».
Ментор выбирает строку, пишет текст замечания и отправляет форму. Страница перезагружается, комментарий отображается
под выбранной строкой, а форма ревью по-прежнему доступна на странице.

**Why this priority**: Без возможности оставить комментарий фича не существует; это основной вклад ментора.

**Independent Test**: Войти ментором, открыть любую сдачу, оставить комментарий к строке и увидеть его под этой
строкой после перезагрузки страницы.

**Acceptance Scenarios**:

1. **Given** ментор открыл сдачу, **When** страница показана, **Then** каждая строка кода имеет видимый номер,
   а у каждой строки есть действие «Комментировать».
2. **Given** ментор выбрал действие «Комментировать» у строки N, **When** страница обновилась, **Then** под строкой N
   показана форма с полем текста комментария и кнопкой отправки, а выбранная строка визуально выделена.
3. **Given** форма комментария к строке N открыта, **When** ментор вводит допустимый текст и отправляет форму,
   **Then** страница сдачи показана снова, комментарий виден под строкой N с именем автора и датой, форма закрыта.
4. **Given** к строке N уже есть комментарий, **When** ментор комментирует эту же строку ещё раз, **Then** оба
   комментария показаны под строкой N в порядке создания (старый выше).
5. **Given** ментор пришёл на сдачу из очереди ревью с фильтром по задаче, **When** он оставляет комментарий,
   **Then** ссылка «← Очередь ревью» по-прежнему ведёт в очередь с тем же фильтром.
6. **Given** у сдачи уже есть ревью, **When** ментор открывает её, **Then** у строк кода есть действие
   «Комментировать», и комментарий создаётся и отображается так же, как на сдаче без ревью (FR-003).

---

### User Story 2 - Ученик видит комментарии рядом со строками своего кода (Priority: P1)

Ученик открывает страницу своей сдачи и видит код с номерами строк. Под каждой строкой, к которой есть
комментарии ментора, показаны эти комментарии (автор, дата, текст). Действий для добавления комментариев ученик не
видит.

**Why this priority**: Ценность фичи для ученика - увидеть замечания у нужных строк; без этого комментарии бесполезны.

**Independent Test**: Оставить комментарий ментором, войти автором сдачи, открыть сдачу и увидеть комментарий под
нужной строкой без кнопок «Комментировать».

**Acceptance Scenarios**:

1. **Given** у сдачи есть комментарии к строкам 3 и 7, **When** ученик-автор открывает сдачу, **Then** комментарии
   показаны под строками 3 и 7, остальные строки без комментариев.
2. **Given** ученик-автор открыл сдачу, **When** страница показана, **Then** действий «Комментировать» и форм
   комментария нет.
3. **Given** ученик не автор сдачи, **When** он открывает её адрес, **Then** он получает ответ «Не найдено», как
   для несуществующей сдачи (поведение US-5 AC2 из baseline не меняется), и комментариев не видит.
4. **Given** ученик-автор открыл сдачу, **When** он пробует отправить комментарий (прямым запросом), **Then** он
   получает отказ в доступе (`403`).
5. **Given** у сдачи есть комментарии, **When** ученик-автор открывает страницу, **Then** текст комментария и код
   выводятся с экранированием HTML.

---

### User Story 3 - Понятные состояния и ошибки (Priority: P2)

Пользователь всегда понимает, что происходит: если комментариев нет, это сказано; если ввод неверный, видна
ошибка у поля, а введённый текст сохранён.

**Why this priority**: Улучшает удобство, но основной сценарий работает и без аккуратных сообщений.

**Independent Test**: Отправить пустой комментарий и убедиться, что показана ошибка у поля с сохранённым вводом;
открыть сдачу без комментариев и увидеть пустое состояние.

**Acceptance Scenarios**:

1. **Given** у сдачи нет комментариев, **When** её открывает ментор или ученик-автор, **Then** страница показывает
   подсказку «Комментариев к строкам пока нет» и без неё остаётся рабочей.
2. **Given** ментор отправил форму комментария с пустым (после обрезки пробелов) текстом, **When** ответ получен,
   **Then** форма остаётся открытой у той же строки, у поля текста показана ошибка, комментарий не создан.
3. **Given** ментор отправил слишком длинный текст, **When** ответ получен, **Then** показана ошибка у поля, введённый
   текст сохранён в поле для исправления.
4. **Given** ментор отправил комментарий к строке, которой нет в коде (номер вне диапазона), **When** ответ получен,
   **Then** страница сдачи показана со статусом `400` и общим понятным сообщением об ошибке, введённый текст
   сохранён, комментарий не создан.
5. **Given** запрошена несуществующая сдача (в том числе с id вне диапазона `INTEGER`), **When** ментор отправляет
   комментарий, **Then** показана страница «Не найдено» (`404`), как в `openspec/specs/path-id-bounds`.

---

### Edge Cases

- Код из одной строки: нумерация, действие «Комментировать» и вывод работают как для любой другой сдачи.
- Код с пустыми строками и завершающим переводом строки: пустая строка тоже имеет номер и может быть
  прокомментирована; нумерация совпадает с нумерацией, видимой пользователю в блоке кода.
- Очень длинная строка кода или очень длинный комментарий: страница остаётся читаемой (перенос или горизонтальная
  прокрутка блока кода), вёрстка не ломается.
- Много комментариев к одной строке: все показаны, порядок - по времени создания.
- В тексте комментария или коде есть HTML/скрипты: показываются как текст.
- Двойная отправка формы (повторный клик): может создать два комментария; защита от дублей не требуется (см. Assumptions).
- Сдача уже имеет ревью: «Комментировать» и форма комментария доступны ментору так же, как на сдаче без ревью (FR-003).
- Ментор, вошедший не под своей ролью, или неавторизованный пользователь: неавторизованный перенаправляется на
  `/login` (baseline US-1 AC3).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Страница сдачи MUST показывать код с видимыми номерами строк для ментора и для ученика-автора.
  Нумерация начинается с 1 и совпадает с номерами, которые используются при создании комментария.
- **FR-002**: Для ментора у каждой строки кода MUST быть доступно действие «Комментировать», работающее без JavaScript
  (отдельный переход или отправка формы с перезагрузкой страницы).
- **FR-003**: Ментору MUST быть доступна форма комментария к выбранной строке независимо от статуса сдачи: на сдаче,
  у которой уже есть ревью, действие «Комментировать» и форма комментария показываются так же, как на сдаче без ревью
  (форма ревью при этом ведёт себя как в baseline и на комментарии не влияет).
- **FR-004**: Форма комментария MUST содержать одно поле текста (обычный текст) и кнопку отправки; поле
  привязано к конкретной строке, которую ментор выбрал.
- **FR-005**: После успешной отправки MUST показываться страница сдачи с новым комментарием под соответствующей
  строкой; повторная отправка формы страницей (обновление) не должна создавать комментарий без явного действия
  пользователя (ответ на отправку - редирект на страницу сдачи).
- **FR-006**: Каждый комментарий MUST показываться под своей строкой кода с автором (отображаемое имя), датой и
  текстом; несколько комментариев к одной строке MUST идти в порядке создания.
- **FR-007**: Строки с комментариями MUST быть визуально отличимы от строк без комментариев.
- **FR-008**: Ученик-автор MUST видеть комментарии к своей сдаче и MUST NOT видеть действий и форм для создания
  комментариев.
- **FR-009**: Для ученика, не являющегося автором сдачи, страница сдачи MUST оставаться неотличимой от страницы
  несуществующей сдачи (`404`), и комментарии не должны раскрываться ни на странице, ни в сообщениях об ошибках.
- **FR-010**: Попытка ученика (любого) отправить комментарий MUST заканчиваться отказом в доступе (`403`) с
  обычной страницей ошибки приложения.
- **FR-011**: Если у сдачи нет комментариев, страница MUST показывать пустое состояние («Комментариев к строкам
  пока нет»); вёрстка кода и формы ревью при этом не меняются.
- **FR-012**: При ошибке проверки ввода форма MUST открываться снова у той же строки с сообщением об ошибке у
  поля, введённый текст MUST сохраняться; ответ - `400`, как для остальных форм приложения.
- **FR-013**: При недопустимом номере строки (не число, вне диапазона строк кода) страница сдачи MUST показываться со
  статусом `400` и понятным общим сообщением об ошибке, введённый текст сохраняется, комментарий не создаётся; при несуществующей сдаче - страницу «Не найдено» (`404`).
- **FR-014**: Текст комментария и код MUST выводиться с автоэкранированием HTML; использование `|safe` запрещено.
- **FR-015**: Страница MUST работать без JavaScript и без сборки фронтенда (серверный рендер Jinja2, стили в
  `app/static/style.css`).
- **FR-016**: Существующее поведение MUST сохраняться: форма и ревью, статусы сдач, очередь ревью с фильтром по
  задаче (`openspec/specs/review-queue`), `404` для id вне диапазона (`openspec/specs/path-id-bounds`),
  `docs/baseline.md` (US-1…US-5).
- **FR-017**: Комментарии MUST быть видны ученику-автору сразу после создания ментором, в том числе пока сдача ещё
  `pending` (отправка ревью для показа не требуется).

### Key Entities *(include if feature involves data)*

- **Комментарий к строке**: замечание ментора к одной строке кода одной сдачи. С точки зрения UI важны: сдача,
  номер строки (с 1), текст, автор (ментор, отображаемое имя), дата создания.
- **Сдача (Submission)**: существующая сущность; комментарии отображаются на её странице, отдельной страницы у
  комментариев нет.
- **Строка кода**: единица отображения; номер строки определяется по тексту кода сдачи и является ключом
  привязки комментария.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Ментор оставляет комментарий к выбранной строке не более чем за 3 действия (выбрать строку, ввести
  текст, отправить) и сразу видит его под нужной строкой.
- **SC-002**: Ученик-автор видит каждый комментарий ментора под правильной строкой на странице своей сдачи в 100%
  проверенных случаев.
- **SC-003**: Ученик ни в одном проверенном случае не видит чужие сдачи и комментарии к ним и не видит способов
  создать комментарий.
- **SC-004**: В 100% проверенных случаев неверного ввода пользователь видит понятное сообщение у поля, а введённый
  текст не теряется.
- **SC-005**: Все сценарии baseline (US-1…US-5), очереди ревью и границ id остаются зелёными (`CHECK: PASS`) после
  добавления фичи.

## Assumptions

- Комментировать могут любые пользователи с ролью `mentor`: именно они вправе оставлять ревью (brief, права; US-4).
  Ученик только читает комментарии своих сдач.
- Серверная сторона (команда логики) отвечает за хранение (новая таблица), права, проверку номера строки и текста,
  порядок комментариев; UI ожидает от неё: комментарии сдачи упорядочены по времени создания; при ошибках проверки
  сервис отдаёт ошибки по полям (как `ValidationError` в остальных сервисах), `Forbidden` для ученика, `NotFound`
  для чужой/несуществующей сдачи.
- Допустимая длина комментария: после обрезки пробелов от 1 до 5 000 символов, как у комментария ревью (US-4 AC2);
  окончательное значение фиксирует команда логики. UI показывает ограничение через атрибут `maxlength` поля и
  сообщение об ошибке с сервера.
- Номера строк считаются от 1 по строкам кода, разделённым переводом строки (как сейчас делит `_code.html`).
- Нескольких комментариев к одной строке достаточно; ограничения на их число нет.
- Серверная сторона (команда логики) отдаёт комментарии сдачи ученику-автору независимо от статуса сдачи, в том числе `pending` (FR-017); UI не фильтрует комментарии по статусу.
- Серверная сторона (команда логики) принимает комментарии к сдаче в любом статусе, в том числе с ревью (FR-003); UI не скрывает действия по статусу сдачи. Если команда логики запретит комментарии после ревью, FR-003 и сценарий 6 истории 1 пересматриваются.
- Редактирование, удаление и черновики комментариев вне рамок (brief); UI не содержит таких действий.
- Общий контракт фичи по конституции должен лежать в `specs/line-comments-contract.md`; на момент написания файла
  нет. Если он появится и будет противоречить этой спецификации, приоритет у контракта, спека корректируется.
- Защита от двойной отправки формы и CSRF-защита не вводятся (в baseline CSRF отсутствует).
- Уведомления ученика о новых комментариях, поиск и фильтрация комментариев вне рамок.
- Выбор строки для комментирования делается переходом по ссылке/кнопке с перезагрузкой страницы (без JS);
  конкретные URL и имена параметров - задача планирования.
- Тесты фичи лежат в `tests/test_line_comments_ui.py` и ссылаются на `FR-NNN` в имени или docstring.
