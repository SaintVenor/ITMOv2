# Proposal

## Why

Ментор сейчас видит в `/review` одну общую очередь `pending`-сдач по всем задачам. Чтобы проверить подряд сдачи одной задачи, ему приходится выискивать их глазами, и после каждого ревью он снова попадает в общую очередь. Фильтр по задаче, который не теряется по пути «очередь -> сдача -> ревью -> очередь», убирает эту рутину.

## What Changes

- `GET /review` принимает необязательный query-параметр `assignment_id`. Если он задан, очередь показывает только `pending`-сдачи этой задачи, старые сверху. Пустое значение (`?assignment_id=`) означает «без фильтра».
- Валидно только каноничное положительное целое в ASCII (`^[1-9][0-9]*$`, не больше 2^63-1). Любое другое значение и несуществующая задача дают `404` «Задача не найдена» (единый ответ). При повторе параметра берётся последнее значение.
- На странице очереди появляется GET-форма: `<select>` по всем задачам, первый пункт «Все задачи» (`value=""`), кнопка «Показать». Форма видна всегда, в том числе при пустой очереди. При активном фильтре заголовок имеет вид «Очередь ревью · <название задачи>» и есть ссылка «Сбросить фильтр» на `/review`.
- Если задача есть, а `pending`-сдач по ней нет, показывается отдельное пустое состояние: «Нет сдач, ждущих ревью, по задаче <название>». Общий текст «Непроверенных сдач нет.» остаётся только для очереди без фильтра.
- Фильтр переходит из очереди на страницу сдачи и обратно:
  - ссылка «Открыть» несёт `?assignment_id=N`, только когда фильтр активен;
  - на странице сдачи ссылка «← Очередь ревью» ведёт в отфильтрованную очередь;
  - форма ревью передаёт фильтр скрытым полем `assignment_id`;
  - после успешного ревью редирект ведёт в `/review?assignment_id=N`.
- URL редиректа собирает сервер только из id проверенной существующей задачи. Произвольный `next=`/URL не принимается, open redirect невозможен.
- На странице сдачи и в POST ревью невалидный или несуществующий фильтр молча игнорируется: ссылка и редирект ведут на `/review`. Студенту параметр безразличен. Несовпадение фильтра с задачей сдачи допускается.

### Изменение существующего поведения

- **BREAKING (наблюдаемое поведение):** сейчас `/review` не знает параметра и молча его игнорирует. Например, `GET /review?assignment_id=abc` сейчас отдаёт `200` с полной очередью, а станет отдавать `404` «Задача не найдена». То же касается любых невалидных и несуществующих значений. Тестов baseline это не затрагивает. В спеке это отдельное требование (RQF-4).
- Ответы `409` (повторное ревью) и `404` (сдача не найдена) после POST по-прежнему рендерят `error.html`. Фильтр в этих ответах теряется, и это осознанное решение.

## Capabilities

### New Capabilities
- `review-queue`: очередь ревью ментора и её фильтрация по задаче, включая сохранение фильтра при переходе к сдаче и после ревью. Базовой спеки нет (`openspec/specs/` пуст), поэтому дельта содержит только ADDED-требования. Поведение baseline из US-4 остаётся источником в `docs/baseline.md`.

### Modified Capabilities
- нет

## Вне рамок

- **Известная проблема B (baseline):** `/assignments/99999999999999999999`, `/submissions/99999999999999999999` и `POST /submissions/99999999999999999999/review` сейчас отдают `500` (OverflowError в SQLite). Этот change её не чинит, потому что менять поведение baseline без поручения нельзя. Новый параметр фильтра этот баг не повторяет: сверхбольшие значения отсекаются до обращения к БД.
- Любые другие правки baseline, `docs/baseline.md` и `scripts/check.sh`.
- Фильтры по ученику и статусу, сортировка, пагинация, счётчики сдач в `<select>`, JS-автоотправка формы.

- `test_us4_ac2_review_saves_verdict_comment_and_updates_status`: без фильтра `Location` ровно `/review`;
- `test_us4_ac2_comment_boundaries_accepted`, `test_us4_ac2_invalid_review_rejected`, `test_us4_ac3_*`, `test_us4_review_of_missing_submission_is_404`, `test_us4_mentor_opens_submission_and_sees_review_form`;
- `test_us4_ac4_student_cannot_review_even_own_submission`, `test_us4_ac4_student_has_no_review_queue_or_form`.

Также остаются зелёными остальные тесты: `tests/test_us1_*`, `test_us2_*`, `test_us3_*`, `test_us5_*` и `test_cli.py`.

## Impact

- Код: `app/services/reviews.py` (разбор и проверка фильтра, фильтрованная очередь), `app/web/review.py` (параметр `/review`, скрытое поле в POST, вызов `review_queue_url` для редиректа), `app/web/submissions.py` (хелпер `review_queue_url` рядом с `render_submission`; `render_submission` и страница сдачи узнают фильтр).
- Шаблоны: `app/templates/review/queue.html`, `app/templates/submissions/detail.html`.
- Тесты: новый `tests/test_review_queue_task_filter.py`.
- Новых зависимостей и изменений модели данных нет. Схема БД не меняется.
