## User Scenarios & Testing *(mandatory)*

### User Story 1 - Ментор комментирует строку кода сдачи (Priority: P1)

Ментор, просматривая код сдачи, указывает номер строки и пишет замечание. Комментарий сохраняется и привязывается к этой строке этой сдачи, чтобы ученик понял, к какому месту относится замечание.

**Why this priority**: Без создания комментариев фича не существует; это основа, на которой строится всё остальное.

**Independent Test**: Ментор отправляет номер существующей строки и текст по чужой для него сдаче ученика; затем запрос списка комментариев сдачи возвращает этот комментарий с тем же номером строки и текстом.

**Acceptance Scenarios**:

1. **Given** сдача с кодом из 10 строк, **When** ментор создаёт комментарий к строке 3 с непустым текстом, **Then** комментарий сохранён и привязан к строке 3 этой сдачи, с автором-ментором и временем создания.
2. **Given** сдача с кодом из 10 строк, **When** ментор создаёт второй комментарий к той же строке 3, **Then** оба комментария сохранены и возвращаются в порядке создания.
3. **Given** сдача с кодом из 10 строк, **When** ментор указывает строку 11 (или 0, или отрицательную, или не число), **Then** комментарий не создаётся, возвращается ошибка валидации у поля номера строки.
4. **Given** корректный номер строки, **When** текст пуст или состоит из пробелов либо превышает допустимую длину, **Then** комментарий не создаётся, возвращается ошибка валидации у поля текста.
5. **Given** ученик, **When** он пытается создать комментарий (в том числе к своей сдаче), **Then** запрос отклонён как запрещённый, комментарий не создаётся.
6. **Given** несуществующая сдача (в том числе id вне диапазона целых SQLite), **When** ментор создаёт комментарий, **Then** ответ «не найдено», как для любой отсутствующей сдачи.

---

### User Story 2 - Ученик читает комментарии к своей сдаче (Priority: P1)

Ученик получает комментарии ментора к своей сдаче, каждый с номером строки, к которой он относится, чтобы интерфейс мог показать их рядом с нужными строками кода.

**Why this priority**: Это вторая половина ценности фичи — без чтения комментарии ученику бесполезны.

**Independent Test**: Ментор оставил комментарии к двум сдачам разных учеников; каждый ученик получает только комментарии своей сдачи, а запрос списка по чужой сдаче неотличим от запроса по несуществующей.

**Acceptance Scenarios**:

1. **Given** у сдачи ученика есть комментарии к строкам 2 и 5, **When** ученик запрашивает комментарии своей сдачи, **Then** он получает их все, каждый с номером строки, текстом, автором и временем, упорядоченные по номеру строки, а внутри строки — по времени создания.
2. **Given** сдача другого ученика, **When** ученик запрашивает её комментарии, **Then** результат тот же, что для несуществующей сдачи («не найдено»), без каких-либо признаков существования сдачи.
3. **Given** у сдачи нет комментариев, **When** её автор запрашивает комментарии, **Then** возвращается пустой список, а не ошибка.
4. **Given** комментарий с HTML-разметкой в тексте, **When** его получает ученик или ментор, **Then** текст отдаётся как обычный текст без интерпретации разметки (экранирование при выводе — на стороне отображения, но данные не изменяются и не «очищаются»).

---

### User Story 3 - Ментор видит комментарии при проверке сдачи (Priority: P2)

Ментор при открытии любой сдачи получает все комментарии, оставленные к ней (в том числе другими менторами), чтобы не дублировать замечания.

**Why this priority**: Улучшает работу ментора, но фича самодостаточна и без этого.

**Independent Test**: Два ментора по очереди комментируют одну сдачу; каждый из них при запросе списка видит оба комментария.

**Acceptance Scenarios**:

1. **Given** комментарии, оставленные ментором A, **When** ментор B запрашивает комментарии той же сдачи, **Then** он видит их все с указанием автора.
2. **Given** запрос без сессии, **When** запрашивается список или создание комментария, **Then** выполняется перенаправление на вход, как на остальных страницах.

---

### Edge Cases

- Код из одной строки: допустима только строка 1.
- Код содержит пустые строки: на пустую строку комментировать можно, она считается строкой.
- Код сохранён с переводами строк `\r\n`: строки считаются по тому же правилу, по которому код уже разбивается для показа (после нормализации `\r\n` в `\n`), чтобы номер строки у ученика и ментора совпадал.
- Номер строки в нечисловом, неканоничном виде (`05`, `+3`, `3.0`, ` 3`, `٣`, `1e1`): считается невалидным.
- Очень большой номер строки (более 2^63-1 и т. п.): невалидный номер строки, а не внутренняя ошибка.
- Id сдачи в пути вне диапазона целых SQLite: «не найдено», как в `openspec/specs/path-id-bounds`.
- Проверка прав раньше разбора входных данных: ученик с невалидным вводом получает «запрещено», а не ошибку валидации; аноним — перенаправление на вход.
- Одновременная отправка нескольких комментариев к одной строке: сохраняются все, потерь нет.
- Новая попытка ученика и повторная сдача: комментарии принадлежат конкретной сдаче (попытке) и не переносятся на другие попытки.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST хранить построчный комментарий как отдельную запись, содержащую: сдачу, к которой он относится; номер строки; текст; автора-ментора; время создания. Комментарий принадлежит ровно одной сдаче.
- **FR-002**: Система MUST хранить комментарии только в новой таблице и MUST NOT изменять схему существующих таблиц (`users`, `assignments`, `submissions`, `reviews`); уже созданная база данных MUST продолжать работать без миграций.
- **FR-003**: Система MUST считать строкой кода сдачи элемент, получающийся разбиением сохранённого кода по символу перевода строки `\n` (так же, как код уже разбивается для показа); строки нумеруются с 1; допустимые номера — от 1 до количества строк кода включительно, пустые строки в том числе.
- **FR-004**: Система MUST позволять создавать комментарий только пользователю с ролью ментора, то есть тому же, кто вправе оставлять ревью (`docs/baseline.md`, US-4); ученик при попытке создания получает отказ «запрещено» (403-класс), комментарий не создаётся.
- **FR-005**: Система MUST принимать номер строки только в каноничном десятичном виде (ASCII-цифры без ведущих нулей, без знака и пробелов, значение не меньше 1); любое другое значение, а также номер больше количества строк кода, MUST отклоняться ошибкой валидации у поля номера строки без создания комментария и без внутренней ошибки.
- **FR-006**: Система MUST принимать текст комментария, длина которого после удаления пробелов по краям составляет от 1 до 2 000 символов; пустой или слишком длинный текст MUST отклоняться ошибкой валидации у поля текста, сообщение указывает допустимую длину и текущую, как у остальных текстовых полей приложения.
- **FR-007**: Система MUST разрешать несколько комментариев к одной и той же строке одной сдачи, в том числе от разных менторов, и MUST хранить и отдавать их в порядке создания.
- **FR-008**: Система MUST по запросу отдавать комментарии сдачи списком; каждый элемент содержит: идентификатор комментария, номер строки, текст, автора (отображаемое имя), время создания. Порядок: по номеру строки, внутри строки — по времени создания (при равенстве — по идентификатору). Для сдачи без комментариев возвращается пустой список.
- **FR-009**: Система MUST позволять ученику получать комментарии только своих сдач; запрос комментариев чужой сдачи MUST давать тот же результат, что запрос по несуществующей сдаче («не найдено»), по аналогии с `docs/baseline.md`, US-5 AC2.
- **FR-010**: Система MUST позволять любому ментору получать комментарии любой существующей сдачи, включая комментарии других менторов.
- **FR-011**: Система MUST давать ответ «не найдено» на создание и чтение комментариев для сдачи, которой нет, в том числе когда id сдачи вне диапазона `INTEGER` SQLite (без обращения к базе и без внутренней ошибки), в соответствии с `openspec/specs/path-id-bounds`.
- **FR-012**: Система MUST проверять сессию и роль раньше разбора и валидации входных данных: запрос без сессии — перенаправление на вход; ученик в операции создания — «запрещено» при любом входе, включая невалидный.
- **FR-013**: Система MUST отдавать и хранить текст комментария как обычный текст: без интерпретации разметки и без изменений содержимого, кроме удаления пробелов по краям и нормализации `\r\n` в `\n`; безопасный вывод (экранирование HTML) обеспечивает слой отображения.
- **FR-014**: Система MUST создавать комментарий атомарно: при любой ошибке валидации, прав или отсутствия сдачи не появляется ни частично созданной записи, ни побочных изменений существующих данных.
- **FR-015**: Создание комментария MUST NOT менять статус сдачи, наличие и содержимое ревью, очередь ревью и нумерацию попыток; существующее поведение `docs/baseline.md`, `openspec/specs/review-queue`, `openspec/specs/path-id-bounds` сохраняется без изменений.
- **FR-016**: Система MUST позволять ментору комментировать сдачу в любом статусе (`pending`, `accepted`, `changes_requested`), независимо от наличия ревью; статус сдачи при создании комментария не проверяется и отдельной ошибки по статусу нет.
- **FR-017**: Ученик MUST получать комментарии своей сдачи сразу после их создания ментором, независимо от статуса сдачи и наличия ревью (в том числе в статусе `pending`); скрытия комментариев до вердикта нет.
- **FR-018**: Для слоя отображения система MUST предоставлять: операцию создания (вход — сдача, номер строки, текст; результат — созданный комментарий или перечень ошибок по полям `line` и `text`), операцию получения списка комментариев сдачи (FR-008) и признак «число строк кода» либо эквивалентный способ узнать допустимый диапазон номеров строк.
- **FR-019**: Ошибки MUST выражаться тем же набором категорий, что и остальные бизнес-правила приложения: «не найдено», «запрещено», «ошибка валидации (с текстом по полю)»; отдельных новых категорий не вводится.

### Key Entities *(include if feature involves data)*

- **Построчный комментарий**: замечание ментора к одной строке кода одной сдачи. Атрибуты: сдача, номер строки (≥ 1), текст, автор (пользователь-ментор), время создания. Связан с «Сдачей» (много комментариев на сдачу) и «Пользователем» (автор). Хранится отдельно от «Ревью»: ревью — одно общее на сдачу, комментариев может быть много.
- **Сдача** (существует): носитель кода; определяет множество допустимых номеров строк и круг пользователей, которым комментарии доступны. Не изменяется.
- **Ревью** (существует): вердикт и общий комментарий; не изменяется и не заменяется построчными комментариями.
- **Пользователь** (существует): роль ментора даёт право создавать, роль ученика — только читать комментарии собственных сдач.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Ментор оставляет комментарий к выбранной строке одним действием (указание строки и текста); 100 % комментариев с корректным вводом сохраняются и затем возвращаются с теми же номером строки и текстом.
- **SC-002**: Для 100 % проверяемых случаев некорректного ввода (строка вне диапазона, неканоничный номер, пустой или слишком длинный текст) комментарий не создаётся и возвращается понятная ошибка у соответствующего поля; внутренних ошибок (5xx) — ноль.
- **SC-003**: Ученик ни в одной проверке не получает комментарии чужой сдачи; ответ по чужой сдаче неотличим от ответа по несуществующей в 100 % случаев.
- **SC-004**: Ученик ни в одной проверке не может создать комментарий, независимо от корректности ввода.
- **SC-005**: После внедрения фичи все существующие тесты baseline и `openspec/specs` проходят без изменений, а уже созданная база данных работает без миграций.
- **SC-006**: Каждое требование FR-001…FR-019 покрыто хотя бы одной автоматической проверкой, ссылающейся на его идентификатор.

## Assumptions

- Правом оставлять комментарии обладает любой пользователь с ролью ментора (как и право оставлять ревью); отдельного права «только автор ревью» не вводится. Все менторы видят комментарии друг друга.
- Номера строк нумеруются с 1 и соответствуют разбиению кода по `\n`, которое уже используется при показе кода; приложение хранит код после нормализации `\r\n` и обрезки пробелов по краям, поэтому завершающего перевода строки в коде нет.
- Максимальная длина текста комментария — 2 000 символов (меньше, чем 5 000 у общего комментария ревью, так как замечание привязано к одной строке); значение подтверждено на этапе clarify.
- Максимальное количество комментариев на сдачу или на строку не ограничивается: автоматического ограничения в брифе нет.
- Код сдачи не меняется после создания (новая попытка — новая сдача), поэтому комментарий не теряет привязку к строке; перенос комментариев между попытками не предусмотрен.
- Редактирование, удаление комментариев и черновики — вне рамок (бриф); решение о «ответах» ученика, уведомлениях и поиске по комментариям также вне рамок.
- От команды UI логика ожидает: слой отображения сам размещает комментарии рядом со строками, экранирует текст, показывает ошибки у полей `line` и `text`, а для ученика не показывает форму создания. Конкретные экраны, маршруты и вёрстка не определяются этой спецификацией.
- Технические детали (схема таблицы, маршруты, сигнатуры сервисов, коды HTTP) определяются на шаге plan в рамках слоёв из `docs/architecture.md`; коды ответов («запрещено» — 403, «не найдено» — 404, валидация — 400) следуют существующим соглашениям приложения.
- Конституция (`.specify/memory/constitution.md`) ссылается на общий контракт `specs/line-comments-contract.md`; в данной worktree этого файла нет, поэтому спецификация опирается только на бриф и проект. При появлении контракта он имеет приоритет, и спецификацию нужно будет с ним сверить.
