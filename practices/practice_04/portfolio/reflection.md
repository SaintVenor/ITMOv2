# Рефлексия по ДЗ 4

Проект выбрал около 21:40: сайт-портфолио на FastAPI. Каркас (сайт, тесты, `check.sh`, `AGENTS.md`, копию TDD-skill, hook, MCP-сервер `portfolio`, шаблон отчёта) подготовил вместе с Claude в чате. В OpenCode делались фича US-3, проверки и отчёт.

Время: окружение ~1 ч, фича US-3 ~10 мин, доказательства и отчёт ~25 мин. Основную часть времени заняла не работа агента, а то, чтобы среда вообще заработала.

## Что мешало

- **WSL без `python3.14-venv`.** `python3 -m venv` упал. apt качал пакет на ~38 kB/s, установка заняла ~10 минут.
- **Шум в выводе runner.** `check.sh` печатал `StarletteDeprecationWarning`, фильтр `DeprecationWarning` его не ловил. До сессии заменил фильтр на `-p no:warnings`. Иначе hook возвращал бы агенту мусор с каждой правкой.
- **Расхождение версий.** `opencode --version` показал 1.18.35, а материалы курса написаны под 2.0.20. Hook был написан в формате V2 (`setup`, `ctx.tool.hook`), и 1.x его бы просто не запустил — молча. Команды `opencode api skill.list` в 1.x нет. Пришлось переписать hook на один файл с `server()` для 1.x и `setup()` для 2.x, перенести его в `.opencode/plugin/`, а skill — в `.opencode/skill/`. Вывод: сначала проверять версию инструмента, потом верить инструкции.
- **Лишние skills в контексте.** Список skills оказался огромным JSON, и через `tee` вывод обрезался. В нём нашлись 14 глобальных skills из `~/.claude/skills` (docx, pdf, morning и др.). Они попадают в контекст агента в каждом запросе, хотя проекту не нужны. Среда агента — это не только то, что лежит в проекте.

## Что помогло

- **`AGENTS.md`.** Агент прочитал его и пересказал правильно: команду проверки, запреты, контракт US-3 с граничными значениями. Правило «нельзя `git add`/`git commit`» реально сработало: попытку `git add -N` OpenCode заблокировал.
- **Свой MCP.** Сработал с первого раза: успех на `walkey` и обработанная ошибка на `react-app`. Ошибка со списком доступных slug полезнее, чем просто «not found»: по ней агент может исправиться без лишних вопросов.
- **Context7.** Перед поиском документации агент сам прочитал `requirements.txt`, чтобы понять версии библиотек. Этого я не просил. Решение со `StringConstraints(strip_whitespace=True, ...)` сразу закрыло правило «после `strip()`».
- **Skill + hook.** Тесты появились раньше кода, первый прогон упал по правильной причине (`404 == 201`), после реализации стал зелёным. Фича заняла ~10 минут.

## Где пришлось вмешаться

1. **Слабые граничные тесты.** Агент проверил границы только изнутри диапазона: 1 и 100, 10 и 2000. Выход за границу (101, 9, 2001, строка из пробелов) не проверялся. Попросил добавить эти тесты. Они прошли сразу, без стадии FAIL, потому что ограничения уже были в коде. Формально TDD тут нарушен: skill сам называет «test passes immediately» red flag. Skill не заменяет ревью: агент следовал процедуре, но выбрал удобные для себя случаи.
2. **Сбор доказательств — самая ненадёжная часть.**
   - Агент заявил, что дифф содержит оба файла. На деле новый `tests/test_contact.py` туда не попал: файл неотслеживаемый, а `git add -N` был запрещён правилом.
   - Вместо того чтобы сообщить, что команда заблокирована, агент попробовал несуществующую опцию `git update-index --intent-to-add`. Потом пересобрал дифф без тестов и написал, что «добавил tests/test_contact.py в интент индексации».
   - При точечной правке `REPORT.md` агент сломал соседние разделы: продублировал строку, удалил заголовок и вставил свой ответ из чата вместо абзаца.
   - Про файл `writing-good-tests.md` на ~200 строк агент написал «15 строк», хотя по логу прочитал его целиком (198 строк).

   Вывод: всё, что агент пишет о своей работе, нужно сверять с сырыми логами и файлами, а не с его пересказом.

## Наблюдения

- Пересказ агента — не доказательство. Агент писал «вывод hook», но проверить это можно было только по `.opencode/hook-log.jsonl` и экспорту сессии: в нём текст `[hook check-after-edit] ... exit 1` виден прямо в результате `apply_patch`. В логе hook поле `file` равно `null`: правки шли через `apply_patch`, а не `edit`/`write`. Hook такого инструмента не учёл.
- Hook стоит делать максимально тихим и детерминированным. Его вывод попадает в контекст после каждой правки, и любой шум (warnings, длинный traceback) агент будет читать каждый раз.
- Агент лучше всего справился с чётко заданной задачей и проверяемым результатом (фича + тесты + `check.sh`). Хуже всего — с «бумажной» работой: собирать доказательства и редактировать отчёт, где нет автоматической проверки.
